# SnapShare: Photo App Scaling Plan

## 1. Assumptions

SnapShare is a photo-sharing application where users upload photos and view a feed containing photos from people they follow.

The following assumptions are used for the calculations:

- Registered users: 10,000,000.
- Daily active users (DAU): 10% of registered users.
- Each daily active user uploads 1 photo per day.
- Each daily active user views 50 feed pages per day.
- Average original photo size: 2 MB.
- Average thumbnail size: 50 KB.
- One year has 365 days.
- A day has 86,400 seconds.
- Peak traffic is estimated at 5 times the average traffic.
- Storage estimates exclude database records, backups, replication, logs, and other overheads.
- All uploaded photos receive one thumbnail.
- For simplicity, storage calculations use decimal units: 1 MB = 1,000 KB and 1 GB = 1,000 MB.

### Daily active users

Daily active users are 10% of the 10 million registered users.

DAU = 10,000,000 × 10%

DAU = **1,000,000 users per day**

## 2. Traffic and Storage Estimates

### A. Uploads per second

Each daily active user uploads one photo per day.

Daily uploads = 1,000,000 × 1

Daily uploads = **1,000,000 photos**

Average uploads per second:

1,000,000 ÷ 86,400 = 11.57

Therefore, the system receives approximately **11.6 uploads per second on average**.

Estimated peak uploads per second:

11.57 × 5 = 57.87

Therefore, peak upload traffic is approximately **58 uploads per second**.

### B. Feed views per second

Each daily active user views 50 feed pages per day.

Daily feed views = 1,000,000 × 50

Daily feed views = **50,000,000 feed views**

Average feed views per second:

50,000,000 ÷ 86,400 = 578.70

Therefore, the system handles approximately **579 feed views per second on average**.

Peak feed views per second:

578.70 × 5 = 2,893.52

Therefore, peak feed traffic is approximately **2,894 feed views per second**.

These estimates count feed-page requests, not the individual photos or image requests generated by each page.

### C. Photo storage per year

Each photo requires:

- Original photo: 2 MB.
- Thumbnail: 50 KB = 0.05 MB.
- Total per uploaded photo: 2.05 MB.

Daily storage:

1,000,000 × 2.05 MB = 2,050,000 MB

Daily storage = **2,050 GB, or 2.05 TB**

Yearly original-photo storage:

1,000,000 × 2 MB × 365 = 730,000,000 MB

Yearly original-photo storage = **730 TB**

Yearly thumbnail storage:

1,000,000 × 0.05 MB × 365 = 18,250,000 MB

Yearly thumbnail storage = **18.25 TB**

Total yearly storage:

730 TB + 18.25 TB = **748.25 TB per year**

This estimate assumes all uploaded photos and thumbnails are retained for a full year. It excludes backups, replicas, and additional copies created for reliability.

## 3. Is SnapShare Read-Heavy or Write-Heavy?

SnapShare is a **read-heavy system** because users request feed pages much more frequently than they upload photos.

The daily workload consists of:

- 1,000,000 photo uploads.
- 50,000,000 feed views.

There are 50 feed views for every photo upload. Feed reads therefore dominate the request volume, although uploads also involve image transfers and background processing.

The architecture should prioritize fast feed delivery through caching, database read replicas, and a CDN. Uploads should be handled reliably through object storage and a background-processing queue so that creating thumbnails does not delay the user's upload unnecessarily.

## 4. Why Photos Should Not Be Stored Inside the Database

Photos are large binary files, and storing them directly inside a relational database would increase database size, backups, and replication overhead. It could also make database maintenance and scaling more expensive.

Instead, original photos and thumbnails should be stored in **object storage**, such as Amazon S3, Cloudflare R2, or another compatible service. The database should store photo metadata, such as the photo ID, owner ID, caption, upload time, and object-storage key.

This keeps the database focused on structured information while object storage handles large files efficiently.

## 6. What Each Component Solves

1. **CDN:** Delivers cached photos and thumbnails from locations close to users, reducing latency and repeated requests to the origin.
2. **Load balancer:** Distributes incoming application traffic across healthy app servers to avoid overloading one server.
3. **App servers:** Handle API requests, authentication, feed logic, upload authorization, and communication with other services.
4. **Cache:** Stores frequently requested feed data and other commonly accessed information to reduce repeated database queries.
5. **Primary database:** Stores structured data, including users, follow relationships, photo metadata, and upload records.
6. **Database read replica:** Serves read queries such as feed metadata retrieval, reducing the read workload on the primary database.
7. **Object storage:** Stores original photos and thumbnails without filling the relational database with large binary files.
8. **Queue:** Holds thumbnail-generation jobs until workers can process them, absorbing bursts of uploads.
9. **Thumbnail worker:** Processes queued jobs, creates smaller versions of uploaded photos, and saves the thumbnails to object storage.

## 7. Step-by-Step Photo Upload Flow

1. A user signs in and selects a photo to upload.
2. The client requests permission to upload the photo from the app server.
3. The app server authenticates the user and checks upload requirements, such as file type and size.
4. The server provides a short-lived upload URL, or accepts the file through the application, depending on the implementation.
5. The client uploads the original photo to object storage. Direct uploads through a signed URL reduce the amount of large-file traffic passing through the app servers.
6. After the upload succeeds, the application records the photo metadata and storage key in the primary database and creates a thumbnail-generation job in the queue.
7. A thumbnail worker takes the job from the queue, retrieves the original photo, and generates a smaller 50 KB thumbnail.
8. The worker stores the thumbnail in object storage and updates the photo record to indicate that processing is complete.
9. The CDN can then serve the thumbnail and original photo to users. Cache headers and invalidation rules help ensure users receive the correct version.
10. The photo appears in the relevant feeds once its metadata and visibility rules allow it to be displayed.

The system should handle failures carefully. Jobs should be retried when appropriate, and duplicate job processing should not create inconsistent records or unnecessary copies.

## 8. Scaling Trade-Offs

### Trade-off 1: Caching versus fresh data

Caching feed data reduces database load and improves response times. However, cached feeds can become temporarily stale when someone uploads a photo or changes a follow relationship. SnapShare must balance freshness against performance by using appropriate cache expiration and invalidation rules.

### Trade-off 2: Database read replicas versus consistency

Read replicas distribute feed queries and reduce pressure on the primary database. However, replication can lag behind recent writes, so a newly uploaded photo might not appear immediately in a feed. The application can read recently changed records from the primary database when immediate consistency is required.

### Trade-off 3: Direct uploads versus application-server control

Uploading directly to object storage reduces app-server bandwidth and makes large uploads easier to scale. However, it requires secure signed URLs, upload validation, and careful handling of failed or abandoned uploads. Routing all uploads through app servers provides more centralized control but consumes more server bandwidth and processing resources.

### Trade-off 4: Asynchronous thumbnails versus immediate availability

A queue and background worker keep uploads responsive and allow thumbnail generation to scale independently. However, thumbnails may not be available immediately after an upload, and the application must handle pending or failed processing jobs.

### Trade-off 5: Storage cost versus redundancy

Keeping original photos and thumbnails improves availability and user experience, but retaining every image increases storage costs. Deleting old content or applying lifecycle policies can reduce costs, but may conflict with user expectations, retention requirements, or future access needs.

## 9. Conclusion

SnapShare has 1 million daily active users, approximately 11.6 average photo uploads per second, 579 average feed views per second, and an estimated 748.25 TB of new photo and thumbnail data per year.

Because feed reads dominate the workload, the architecture uses a CDN, cache, load balancer, scalable app servers, and a database read replica to serve users efficiently. Object storage handles the large image files, while a queue and background workers create thumbnails without slowing down uploads. This design can scale as the user base and photo collection grow, while acknowledging trade-offs involving consistency, freshness, processing delays, and storage costs.
